# Rail IQ — Prediction Backend

A real, trained ETA-prediction service — not hardcoded numbers. Covers Steps
1–3 of the brief.

## What's real vs. synthetic

- **12805 Janmabhoomi Express** — real historical data, parsed directly from
  the Excel export (Aug 1 – Sep 4 2026, 25 stations × 35 days = 875 rows).
- **12806, 12727, 12841, 20704, 22691** — realistic station/distance/schedule
  skeletons (real Indian Railways trains and routes), with **synthetic**
  delay histories generated by a structured random-walk model (autocorrelated
  delay, rush-hour congestion, ~6% chance of a major incident per journey —
  mirrors the real Aug-31 214-minute outlier seen in the Janmabhoomi data).
  This is the fallback the brief itself describes in Step 1.3, since live
  GPS/NTES scraping isn't reachable from a sandboxed environment. Be upfront
  about this split with judges — it's a defensible, honest position.

Regenerate anytime: `python data/generate_dataset.py`

## The model

`train_model.py` trains a LightGBM regressor (falls back to sklearn
GradientBoostingRegressor if LightGBM isn't available) on:

- `prev_delay` — delay recorded at the previous station
- `distance_to_next_km` — distance of the leg into this station
- `hour_of_day`, `dow` — time-of-day / day-of-week
- `stations_from_origin` — how far into the journey
- `train_id` (encoded) — which train

predicting `delay_minutes` at the next station. Split 80/20 **by whole
journey** (not by row) so the test set is genuinely unseen journeys.

Be honest about this number in a pitch: the RMSE is pulled up by rare,

— the ±5/±10 min hit-rates are the more representative "does this work day
to day" numbers. Retrain any time with `python train_model.py`.

## Running locally

```bash
pip install -r requirements.txt
python data/generate_dataset.py        # builds data/training_data.csv
python data/build_station_reference.py # builds data/stations_reference.json
python train_model.py                  # trains model.pkl
uvicorn main:app --reload --port 8000
```

Try it: `curl "http://localhost:8000/predict-eta?train_id=12805&current_station_no=8&current_delay=12"`

## API

- `GET /trains` — every train the model knows, with its station list
- `GET /predict-eta?train_id=...&current_station_no=...&current_delay=...` —
  predicts delay + ETA at every remaining station, feeding each prediction
  back in as the next station's input (inference, not retraining)

## Deploying (Render, free tier)

1. Push this `rail-iq-backend/` folder to its own GitHub repo (or a
   subfolder — Render lets you set a root directory).
2. On [render.com](https://render.com): New → Web Service → connect the repo.
3. Render auto-detects `render.yaml` — build/start commands are already set.
4. Deploy. You'll get a URL like `https://rail-iq-api.onrender.com`.
5. On the frontend, set `VITE_API_BASE_URL=https://rail-iq-api.onrender.com`
   in Vercel's environment variables and redeploy.

Free-tier Render services sleep after 15 min idle — the first request after
a sleep takes ~30–50s to wake up. Worth mentioning to judges if it comes up
live; not a bug, just the free tier.
